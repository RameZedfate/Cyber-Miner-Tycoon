## 三、⚠️ 三件搬過去會變差的事（先知道，才不會被騙）

### 1. 理賠申請書**產不出 PDF**

本機那套能填出 PDF，是因為有三樣東西：**空白表單 PDF、驗證過的座標、PyMuPDF 引擎**。
Spark 這邊沒有空白表單，也不保證跑得動那支 Python。

所以 Spark 版只能給你**逐欄填寫對照表 + 制式事故敘述**，你自己抄進表單。
規則（不填事故時間地點、地址先問、簽名日期留空、交付即完整版）全部完整保留。

> 👉 **要真的產出 PDF，還是回本機那套。** 這是 Spark 目前明確做不到的事。

### 2. 自動發文做不到

`publisher` 靠 Blotato MCP 排程發文。Spark 沒有 IG／Threads 的發文連接器。
Spark 能幫你**準備好**，按下發布還是你自己來 —— 這件事沒有變。

### 3. 生圖是不同的東西

`social-creative-designer` 是靠 Nano Banana MCP 做「品牌視覺一致」的圖。
Gemini 內建的生圖能力不一樣，套不上你那兩套模板（`#F2EBE0` 米色／`#0E2A47` 深藍）。
硬用會得到「風格不像你的帳號」的圖，反而傷辨識度。**建議視覺繼續用你現在的做法。**

## 四、✅ Spark 能做、而 Claude Code 做不到的四件事

這才是把技能樹搬過去的真正理由。

### 1. **它自己會動**（最大的差別）

Claude Code 要你開對話它才動。Spark 可以排程 —— 平日早上 8 點提醒你今天發哪一支、
週日 10 點準備下週七支腳本、月底自動跑成效檢討。
你的連載最大的風險是**斷更**，而斷更幾乎都發生在「每天現做」的帳號。
`daily-reels-ops` 這個技能就是為這件事寫的。

### 2. **它連得到你的 Google 帳號**

Gmail、Google 日曆、雲端硬碟、試算表都是原生連接器，不用裝 MCP、不用設定。
你原本的 `project-manager` 子代理列了一堆 Google Calendar MCP 工具名稱，
但 `CLAUDE.md` 自己標「未經驗證」—— 在 Spark 這件事直接就成立了。

### 3. **文件歸檔可能反而更好**

原版卡在「只能在本機 Windows 跑」，而且用姓名最後兩個字比對會配錯客戶。
Spark 有雲端硬碟連接器 + Gemini 自己的視覺辨識，理論上可以在雲端跑完整條流程。

> ⚠️ 但這也代表**客戶文件會進 Google 的雲端**。原版的 Windows OCR 是離線的，這是實質的隱私差異。
> 這個取捨要你自己決定，不要因為方便就預設接受。

### 4. **它能主動推播到手機**

「今天該發 Day 12 了，腳本在這」直接推到手機，比你想起來要打開電腦有用得多。

## 五、建議的測試順序

不要一次全部上傳。這樣測最快知道 Spark 到底行不行：

1. **先貼 `01-個人化脈絡.md`** → 隨便問一句「幫我想三個明天可以發的題目」
   → 看它有沒有自動避開工具名開頭、有沒有給具體痛點。**這一步就能看出它有沒有真的讀進去。**
2. **上傳 `adam-brand-context` + `reels-script-writer`** → 叫它寫一支 Day X 腳本
   → 比對本機 Claude 寫的品質。
3. **上傳 `daily-reels-ops` 並設一個每日排程** → 這是 Spark 唯一無法被取代的能力，先驗證這個。
4. **保險相關的最後再測**，而且**第一次用假資料**。

> 前三步都通過，才值得考慮把保險文書也搬過去。
