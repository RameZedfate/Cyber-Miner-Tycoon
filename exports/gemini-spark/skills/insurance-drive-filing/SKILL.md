# 保險文件歸檔（Spark 版）

原始版本靠 Windows 內建 OCR 跑 PowerShell 腳本，只能在本機 Windows 執行。
Spark 版改用**你自己的視覺辨識 + 雲端硬碟連接器**，做的是同一件事，但要遵守同一套安全規則。

## 🔴 最重要的一條規則

**第一次分類絕對不搬檔。** 一定先出建議表給使用者逐列看過。

**沉默不等於同意。** 使用者沒有明確說「這幾列可以搬」就不要動任何檔案。
「看起來對」「嗯」「OK 了嗎」都不算核准 —— 要拿到具體的列號或明確的全部核准。

## 核心流程

1. 讀收件匣資料夾裡的照片，辨識每張的**人名**與**文件類別**
2. 產出建議表（一列一個檔案）
3. 跟使用者一起逐組看過
4. 依使用者的更正重新產生建議表
5. **只搬 `核准搬移 = Y` 的列**
6. 搬完回報：收件匣剩幾個檔、各目的地各增加幾個檔

### 建議表欄位（固定，不要自己改）

```
編號 | 原檔名 | 辨識到的人 | 類別 | 建議路徑 | 信心度 | 判斷依據 | 核准搬移
```

- **信心度**只有三個值：`high` / `low` / `review`
- **判斷依據**要寫「從哪裡看到的」（例：「申請書抬頭姓名欄」「延續第 3 張的同一組」）
- **核准搬移**預設全部空白，由使用者填 `Y`

## 資料夾結構

支援兩種：

```text
客戶\類別
客戶\家庭成員\類別
```

類別固定四種：**理賠**、**保全**、**新契約**、**個人文件**。

日期用民國格式加點，例如 `115.06.10`（不要用斜線）。

## 連號分組

連續編號的照片視為同一份文件組，直到出現不同的人或新的主文件。

- 以第一張「明確有人名」的文件當這組的錨點
- 後面的收據、證明、存摺、身分證背面沒重複出現姓名時，繼承錨點的人
- **中斷繼承的條件**：編號不連續、辨識到不同的人、出現新的申請書或主文件
- 存摺或身分證出現在理賠序列中間時，跟著該次理賠走，除非使用者明講它是獨立文件
- **使用者的更正永遠大於你的辨識結果**

## ⚠️ 姓名比對的陷阱（原始版本的已知風險，這裡一定要避開）

原本的腳本找不到完全相符的名字時，會退而用**姓名最後兩個字**比對。
「陳志明／林志明」這種就會**配到錯的客戶** —— 等於 A 客戶的診斷書被歸進 B 客戶資料夾，**這是個資外洩**。

**Spark 版的做法**：
- 只接受**完整姓名相符**的資料夾
- 名字只有部分相符（同名不同姓、少一個字、疑似錯字）→ 信心度標 `review`，**列出所有候選資料夾讓使用者選**，不要自己挑一個
- 手寫字跡看不清楚 → 標 `low`，寫下你看到什麼、不確定哪個字

> 建議表不可以整欄填 `Y`。特別是 `low` 與 `review` 那幾列，一定要逐列看。

## 這些情況一律先問，不要自己決定

- 辨識到的人在客戶資料夾裡找不到
- 存摺不確定是獨立的個人文件還是理賠附件
- 光靠圖片內容與前後順序無法判斷類別或目的地
- 建議路徑需要**新建**客戶資料夾或家庭成員資料夾

## 🔒 隱私邊界

文件內容與辨識結果都屬於敏感資料。**不要**把以下任何一項寫進會被分享或發佈的地方
（公開文件、Email 草稿、共用資料夾、程式碼、這份技能本身）：

- 客戶或家屬姓名
- 病名、診斷內容、理賠日期
- 文件影像或辨識出來的文字全文
- Email、帳號密碼、token
- 特定客戶的檔名對應規則

搬檔時**只做搬移**：不要覆蓋、不要刪除、不要改檔名以外的內容、不要變更任何檔案的共用權限。
