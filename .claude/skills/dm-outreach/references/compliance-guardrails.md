# 紅線與限制（Compliance Guardrails）

> 三個層次：**平台規則**、**保險法規**、**個資**。三個都踩得到，而且後果不一樣：
> 平台 → 封號；法規 → 停止招攬處分；個資 → 客戶信任與法律責任。

---

## 一、平台層：為什麼這個技能不代發訊息

### 技術現實（2026 年 7 月查證）

1. **冷私訊沒有合規的 API 路徑。**
   Instagram Messaging API 只能在使用者**主動互動後的 24 小時內**回覆
   （對方留言、回限動、傳私訊、點廣告 CTA 才算觸發）。單純按讚**不算**觸發。
   也就是說：**「主動私訊一個沒互動過的人」這件事，API 做不到。**

2. **自動化群發是封號風險最高的行為。**
   Meta 對 cold DM blasting 的處理是直接停權，且 2024 年起自動化訊息速率上限已從
   每小時 5,000 降到 **每小時 200**。專門做 DM 自動化的第三方工具同樣受這條限制。

3. **`HUMAN_AGENT` 標籤可以把窗口延長到 7 天，但 Meta 明文禁止用在自動訊息上**，
   而且有偵測機制。用它來繞過 24 小時窗口做自動私訊 = 明知故犯。

### 結論

> **對 Adam 的實際做法（手動私訊 ＋ 限動回覆）而言，「AI 草擬、人工發送」不只是保守選擇，
> 而是唯一能長期做下去的做法。** 自動化在這個場景既做不到（技術）也不該做（政策）。

而且從效果面看：限動回覆的價值來自「你真的看了那則限動」（見 reply-playbook 加分 2），
自動化必然退化成罐頭訊息 —— **把這件事自動化，等於把它做爛**。

### 手動發送的安全配額（非官方數字，保守估計）

Meta 沒有公布明確的每日上限，而且會依帳號年齡、過往行為動態調整。公開觀察與實務經驗的保守值：

| 動作 | 建議上限 | 說明 |
|---|---|---|
| 新開場私訊（沒互動過的人） | **每天 10-15 則，分散在一天內** | 這是最容易觸發限制的行為 |
| 限動回覆 | 每天 5-10 則 | 屬於「回應」，風險低於冷開場 |
| 既有對話回覆 | 不設限 | 雙向對話幾乎不會觸發 |

**額外的安全規則：**
- 不要在短時間內連發（例如 10 分鐘內傳 10 個人）→ 這是最明顯的機器人特徵
- 不要對多人送**完全相同**的文字 → 重複內容偵測
- 新帳號、或很久沒私訊的帳號，要**慢慢加量**，不要突然開始大量私訊
- 被限制過一次之後，門檻會變低，**恢復期完全停止新開場**

## 二、保險法規層

### 適用規範

- 《保險業務員管理規則》第 19 條 —— 招攬行為的禁止事項與懲處
- 《保險業招攬及核保理賠辦法》
- 《保險業招攬廣告自律規範》第 4 條之 1 —— 網路招攬廣告的處理原則
- ⚠️ **以及永達自己的內部社群規範**（見下方）

### 第 19 條裡跟私訊直接相關的幾款

| 款項要旨 | 對私訊的意義 |
|---|---|
| 就影響要保人權益之事項為**不實說明或不為說明** | 私訊裡講一半的商品說明特別危險 —— 文字容易被解讀成「只講了好的」 |
| 以**誇大不實之宣傳、廣告或其他不當方法**招攬 | 「這個一定賠」「保證領回」這類話，打成文字就是白紙黑字的證據 |
| 招攬**未經核准或備查**之保險商品 | 只能談所屬公司／保經代理的商品 |

> ⚠️ 上述為要旨整理，**不是法條全文**。實際條文以
> [全國法規資料庫](https://law.moj.gov.tw/LawClass/LawSingle.aspx?pcode=G0390016&flno=19) 為準。

### 對私訊草稿的具體規則

| 規則 | 原因 |
|---|---|
| **不寫保額、費率、報酬率、理賠條件、商品比較** | 這些構成「招攬廣告」，須用公司審閱通過的版本 |
| **不自製商品文宣圖／說明文字** | 業務員不得自行製作商品廣告；要用公司提供的版本 |
| **不寫「一定」「保證」「絕對」「穩賺」** | 誇大不實的直接證據 |
| **不做同業商品的貶低比較** | 不當招攬 |
| **不隱瞞身分**（被問到要如實說） | 第 1-2 階「不主動提」跟「被問了否認」完全是兩回事，後者是不實說明 |
| **私訊只談到「約時間」為止**，實質內容進入正式招攬流程 | 私訊留下的文字紀錄會被完整保存，而且可能被截圖 |

> 🔑 **一句話原則：私訊可以聊「人」，不可以聊「商品」。**
> 一旦要談商品，就換到正式的招攬場合（面談 ／ 公司系統 ／ 審閱過的文件）。

### ⚠️ 永達的內部規範優先

多數保經／保險公司對業務員的社群使用另有規範，常見的包括：
- 社群帳號要事前報備／登錄
- 社群發文提及公司或商品要走審閱
- 禁止在個人帳號刊登商品資訊

**這份文件是通則，不能取代永達的內部規定。**
第一次要在 IG／FB 上做保險相關的招攬動作之前，**先問內勤或法遵確認公司規範**。
規範內容確認後請寫進 `context/outreach-profile.md`，之後所有草稿以公司規範為準。

## 三、個資層

### ⚠️ 這個 repo 是 public 的

`RameZedfate/Cyber-Miner-Tycoon` 目前是**公開倉庫**。任何 commit 上去的東西全世界都看得到，
而且 **git 歷史刪不乾淨** —— push 上去再刪除，舊 commit 仍然查得到。

### 硬性規則

| 絕對不可以進 git | 應該怎麼做 |
|---|---|
| 真實姓名 | 代號 `P-001` / `R-001` |
| IG／FB 帳號、暱稱 | 代號 |
| 電話、Email、地址、生日、身分證 | 完全不記錄 |
| 保單號碼、投保內容、理賠案件細節 | 完全不記錄 |
| 任職公司名稱 | 改成類別（「科技業」「餐飲業」） |
| 對話原文（含可識別內容） | 只記「講了什麼類型的事」 |

### 代號對照表放哪裡

```
context/private/roster.md     ← 真名 ↔ 代號，已加入 .gitignore，不會被推上去
outputs/outreach/prospects.md ← 只有代號，可以進 git
```

> ⚠️ `context/private/` 只存在於**你自己的電腦**。雲端 Claude 的容器是暫時的，
> 這個檔案不會同步，也**不應該**同步。雲端 Claude 看不到真名是正確的設計，不是缺陷。

### 使用者在對話裡講到真名怎麼辦

沒關係，可以繼續討論。但是：
1. **寫進檔案時一律換成代號**
2. 第一次發生時提醒一句：「我把他記成 P-007，真名你自己記在本機的 roster」
3. **不要**把含真名的內容寫進任何會被 commit 的檔案，包含 `SHARED_MEMORY.md`

## 四、送出前的三層檢查

```
□ 平台：今天新開場超過 15 則了嗎？這則跟前一則間隔夠久嗎？跟別人送的是不是同一句話？
□ 法規：這則有沒有商品內容／數字／「保證」類字眼？被問身分我有沒有如實回答？
□ 個資：我等一下要寫進追蹤表的內容，有沒有可識別資訊？
```
